PHASE 4 – GLOBAL LOG ROUTING (all pages feed the monitor)
Goal: Redirect every console message from all application pages into the
      same IndexedDB used by testing.html, and silence the browser console
      globally.
4.1 – MINI LOGGER INJECTED INTO ed-french-ini.js
   File: ed-french-ini.js
   Change: Added a `logToDB(storeName, entry)` function that writes to
           'adminMonitorDB_v2' (same DB as testing.html). It opens the DB
           on first use and handles errors silently.
           All previous `console.log/warn/error` calls were replaced with
           calls to `logToDB`.
           A global console override was added at the top of the IIFE:
             ['log','warn','error','info','debug'].forEach(method => {
                 console[method] = function(...args) {
                     const message = args.map(a => ...).join(' ');
                     logToDB(method==='error'?'errors':'actions', {
                         message, level: method, source:'console'
                     });
                 };
             });
           This ensures that even browser-generated warnings (like DOM
           autocomplete suggestions) are captured and silenced.
           Additionally, a Service Worker message listener was added:
             navigator.serviceWorker.addEventListener('message', event => {
                 if (event.data?.type === 'SW_LOG') {
                     const { level, message } = event.data.payload;
                     logToDB(level==='error'?'errors':'actions', { message, source:'sw', level });
                 }
             });
   Reason: Before this change, only testing.html had silent logging; other
           pages still emitted console messages. Now every page in the app
           feeds the monitoring database and remains completely silent.
4.2 – SILENT LOGGING IN cards-building.js
   File: cards-building.js
   Change: Replaced any implicit console usage with the same `logToDB`
           pattern. An initial log entry is written when cards are rendered.
   Reason: Ensures that card-building actions and any errors are recorded
           without console noise.
4.3 – SERVICE WORKER SILENT LOGGING
   File: sw.js
   Change: All `console.log/warn/error` calls were replaced with a helper
           function `swLog(level, message)` that posts a message to all
           clients via `self.clients.matchAll()`. The main thread listener
           (added in 4.1) catches these messages and stores them.
   Reason: The service worker cannot access IndexedDB; messaging is the
           standard way to communicate with pages. Now SW lifecycle events
           and fetch errors are logged in the admin dashboard without any
           console output.
Result: The entire application (all pages + service worker) now operates
        silently. All logs are accessible exclusively via testing.html.
        The only exception is the initial SW registration message, which
        can also be captured if needed (it is routed to DB as well).

PHASE 7 – INSTALL BUTTON FIX
Goal: The “Installer” button sometimes showed a generic “use the browser
      menu” toast instead of the native PWA install prompt. The root cause
      was that the beforeinstallprompt event listener was registered too
      late.
7.1 – MOVED beforeinstallprompt LISTENER TO TOP LEVEL
   File: ed-french-ini.js
   Change: The `window.addEventListener('beforeinstallprompt', …)` block
           was moved from inside `initInstallButton()` (which only runs
           after DOMContentLoaded) to the top level of the IIFE, right
           after the `deferredPrompt` variable declaration. The listener
           now captures the event the moment the browser fires it.
   Reason: Chrome can fire `beforeinstallprompt` very early, sometimes
           before the DOM is ready. With the old placement, the event was
           often missed, causing the fallback toast to trigger.
7.2 – BUTTON VISIBILITY TIED TO PROMPT AVAILABILITY
   File: ed-french-ini.js
   Change: In the `beforeinstallprompt` handler, after storing the event
           in `deferredPrompt`, the code now looks for `#installBtn` and,
           if found, sets its display to `inline-flex`. In
           `initInstallButton()`, if `deferredPrompt` is already non‑null
           when the function is called, the button is immediately shown.
   Reason: The install button should only appear when the browser can
           present a native install dialog. Hiding it by default and
           revealing it only after `beforeinstallprompt` fires ensures the
           user never sees a confusing fallback message.
7.3 – FALLBACK TOAST KEPT AS LAST RESORT ONLY
   File: ed-french-ini.js
   Change: The `else` branch in the install button’s click handler (which
           calls `showToast('toast_install_prompt')`) remains but is now
           only reached if the button is somehow clicked without a prompt
           – a scenario that should no longer happen after the fix.
   Reason: Retains a safety net, but the primary path now reliably opens
           the native install prompt.
7.4 – ALREADY‑INSTALLED CHECK RETAINED
   File: ed-french-ini.js
   Change: The check `window.matchMedia('(display-mode: standalone)').matches`
           remains at the start of `initInstallButton()`. If the app is
           already installed, the button is permanently hidden.
   Reason: Prevents showing an install button for a PWA that is already
           on the user’s home screen.

   File: semaine1-classes-grammaticales.html (inline <script>)

   Research: The top navigation bar (<nav class="back-nav">) is already

        - <th data-i18n="table_word" class="no-bilingual">
        - <th data-i18n="table_answer" class="no-bilingual">
8.5 – JAVASCRIPT OVERRIDE TO HANDLE .no-bilingual ELEMENTS
   File: semaine1-classes-grammaticales.html (inline <script> after ed-french-ini.js)
   Change: Wrapped the global applyTranslations function. The new version:
           1. Calls the original applyTranslations(lang) to restore French
              and insert bilingual spans where appropriate.
           2. Immediately afterwards (via setTimeout(0)), it selects all
              .no-bilingual elements and:
              a) Removes the sibling <span class="i18n-bilingual"> if it exists.
              b) If the current language is not French, replaces the
                 element’s innerHTML with the sibling’s innerHTML (the
                 translation) before removal.
           3. Also runs the same cleanup on initial page load (after a
              short timeout) to catch elements that were processed during
              the initial call.
   Reason: The bilingual system always adds a sibling span containing the
           translation after the original French element. For direct‑only
           elements, that span must be removed, and the French must be
           replaced by the translation when the language is not French.
           Doing this in a post‑processing step keeps the existing i18n
           architecture intact while providing a simple opt‑out mechanism
           via the CSS class.
8.6 – REMOVAL OF PROBLEMATIC CSS HIDE RULE (if previously added)
   Note: In some iterations a CSS rule (.no-bilingual + .i18n-bilingual { display: none; })
         was considered but ultimately rejected because it only hid the
         bilingual span without replacing the text, leaving the French
         visible when another language was selected. The final solution
         relies entirely on JavaScript removal and content replacement,
         so no such CSS rule exists in the final file.
   Reason: Hiding is insufficient; the element must actually contain the
           translated text.
8.7 – PRESERVATION OF ALL ORIGINAL FUNCTIONALITY
   The custom audio player, dynamic exercise table generation, correction
   toggles, dark mode, and all other JavaScript/logic were left untouched.
   Only the i18n hooks and the direct‑translation fix were added.
8.8 – CONSOLE SIMULATION SCRIPT FOR file:// TESTING
   For developers testing locally without a server, a quick console script
   was created to simulate a language change:
     const lang = 'en';   // or 'ar'
     localStorage.setItem('lang', lang);
     if (typeof applyTranslations === 'function') applyTranslations(lang);
     const langSelect = document.getElementById('langSelect');
     if (langSelect) langSelect.value = lang;
   This mimics what the language selector does and allows manual testing
   of all translations and the direct‑translation fix.
Result: The lesson page now correctly switches between French, English, and
Arabic. The first paragraph, footer navigation, and table headers translate
directly without any residual bilingual spans. Table layout remains intact.

PHASE 11 – SERVICE WORKER CACHE STRATEGY FIX
Goal: Stop serving outdated cached HTML/CSS/JS when a new version is
      deployed, while still providing offline fallback.
11.1 – NETWORK‑FIRST FOR DYNAMIC ASSETS
   File: sw.js
   Change: The fetch handler now differentiates:
           - Navigations (HTML pages) → `networkFirst()`: try network,
             update cache, fallback to cache (or `/index.html` if offline).
           - CSS, JS, JSON, manifest → `networkFirst()`: always fetch
             latest, cache the response for offline use.
           - Images, fonts → `cacheFirstThenNetwork()`: serve from cache
             instantly, refresh cache in background.
           - Other requests → timeout‑based network with cache fallback.
           The `serveStaleWhileRevalidate` helper was removed.
   Reason: The old stale‑while‑revalidate strategy could serve an outdated
           index.html or stale JavaScript, causing users to see old
           versions even after a new deploy. Network‑first ensures that
           users always get the latest content when online.
11.2 – ACTIVATION IMPROVEMENTS
   File: sw.js
   Change: On `activate`, after cleaning old caches, the SW now claims all
           clients and posts `SW_UPDATE` to every open tab.
   Reason: Combined with the existing `SW_UPDATE` toast handler in
           ed-french-ini.js, users immediately see the “new version
           available” prompt when the new service worker takes control.
Result: The service worker no longer serves stale resources. All pages
        load the most recent version when online, and offline fallback
        remains intact.

  **Phase 24 – Profile Management Integration**  
Goal: Establish a `profiles` table in Supabase, automatically create a profile on sign‑up (via a trigger), pass the username from the sign‑up form into the metadata, and build a profile modal in the app that displays the user’s username and email.

**24.1 – Created `public.profiles` table with trigger**  
   **File:** SQL executed in Supabase SQL Editor  
   **Change:**  
   ```sql
   -- Table
   CREATE TABLE public.profiles (
       id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
       username TEXT UNIQUE,
       created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
       updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
   );
   ALTER TABLE public.profiles ENABLE ROW LEVEL SECURITY;
   -- Policies
   CREATE POLICY "Users can view own profile" ON public.profiles FOR SELECT USING (auth.uid() = id);
   CREATE POLICY "Users can insert their own profile" ON public.profiles FOR INSERT WITH CHECK (auth.uid() = id);
   CREATE POLICY "Users can update own profile" ON public.profiles FOR UPDATE USING (auth.uid() = id) WITH CHECK (auth.uid() = id);
   -- Trigger function
   CREATE OR REPLACE FUNCTION public.handle_new_user()
   RETURNS TRIGGER LANGUAGE plpgsql SECURITY DEFINER SET search_path = ''
   AS $$
   BEGIN
       INSERT INTO public.profiles (id, username)
       VALUES (NEW.id, NEW.raw_user_meta_data ->> 'username');
       RETURN NEW;
   END;
   $$;
   -- Trigger
   CREATE TRIGGER on_auth_user_created
       AFTER INSERT ON auth.users
       FOR EACH ROW EXECUTE FUNCTION public.handle_new_user();
   ```  
   **Reason:** Every authenticated user needs a profile row. The trigger reads the `username` from the metadata sent during sign‑up and inserts it automatically. RLS ensures users only see their own profile.
